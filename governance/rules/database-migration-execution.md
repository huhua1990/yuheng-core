# 数据库迁移执行与保护规则

适用范围：迁移脚本执行顺序、环境控制、评审验收

先核实目标工程已接入的迁移工具、配置和命令。以下 Liquibase 约束不证明 core 已有对应运行环境；执行真实环境操作须符合用户授权。前置条件校验或执行异常应停止并记录，不用 `MARK_RAN` 将错误伪装成成功。

---

## 强制规则

### 1. 已执行过的 Liquibase changeset / SQL 文件禁止修改

- 不允许改内容
- 不允许删文件
- 不允许手工改 `DATABASECHANGELOG` 或 `DATABASECHANGELOGLOCK`
- 不允许用清 checksum 的方式掩盖历史脚本被改写

### 2. 迁移执行必须按主 changelog include 顺序与版本号顺序进行

- 不允许跳号
- 不允许并行提交互相冲突的版本号
- 同一业务变更的版本号必须一致

### 3. 环境推进必须遵循先低后高

- 先开发环境
- 再测试/联调环境
- 最后生产环境

### 4. 命中基础表或高风险变更时必须中止并升级确认

- 命中 `system_`、`infra_` 直接视为高风险
- 大批量数据修复、删表、删列、重命名也视为高风险

---

## 常见问题处理

- **校验失败**：先核对是否误改已执行 changeset / SQL，再决定是否需要新增修复 changeset
- **Liquibase lock 未释放**：先确认是否存在仍在运行的迁移进程，不要直接手工删锁表记录
- **版本冲突**：重新分配版本号，不要强行覆盖
- **执行失败**：如果脚本尚未在共享环境成功执行，可修复当前新脚本；如果已执行成功，必须新增修复 changeset

---

## 交付前最少验证

- 当前脚本版本号是否唯一
- changeset / SQL 目录是否正确
- 主 changelog 是否 include 了新 changeset
- changeset 引用的 SQL 文件是否真实存在
- 是否提供执行顺序说明
- 是否说明了影响范围与回滚方式
- 是否明确没有触碰基础表

---

## AI 行为约束

- 发现修改基础表时必须拒绝直接生成 SQL
- 发现已执行 changeset / SQL 被改写时必须指出风险
- 如果无法确认当前最大版本号，必须先搜索现有迁移目录再给出脚本名
