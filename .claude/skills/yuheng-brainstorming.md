# Yuheng Brainstorming

将创意想法转化为完整的设计和规格，通过自然协作对话完成。

先理解当前项目上下文，然后逐个问题澄清想法。理解要构建什么后，展示设计并获得用户批准。

<HARD-GATE>
在展示设计并获得用户批准之前，禁止调用任何实现 Skill、编写任何代码、脚手架任何项目或采取任何实现行动。
这适用于每个项目，无论看起来多么简单。
</HARD-GATE>

---

## 反模式："这太简单不需要设计"

每个项目都要经过这个流程。待办事项列表、单功能工具、配置修改——全部都要。

**为什么**:
- 即使是"简单"任务，设计也能暴露隐藏的复杂性
- 防止在错误方向上浪费时间
- 确保与现有系统一致
- 创建可追溯的决策记录

---

## 核心流程（9步）

### 步骤 1: 探索项目上下文

理解现有系统和约束：

1. **阅读项目文档**
   - README
   - 架构文档
   - 相关规格

2. **检查相关代码**
   - 现有功能实现
   - 命名约定
   - 架构模式

3. **识别约束**
   - 技术栈限制
   - 性能要求
   - 安全考虑

### 步骤 2: 逐个澄清问题

**一次一个问题**。不要列出问题清单。

**问题类型优先级**:
1. 多选题（最容易回答）
2. 是/否问题
3. 开放性问题（最后使用）

**示例**:
```
Q: 这个功能主要给哪类用户使用？
   A) 管理员
   B) 普通用户
   C) 两者都是
```

### 步骤 3: 提出 2-3 种方案

**必须提供多个选项**，不要只给一个方案。

**每个方案包含**:
- 核心思路
- 优势
- 劣势
- 实现复杂度

**示例**:
```markdown
## 方案 A: 单表存储
- 优势: 简单，查询快
- 劣势: 扩展性差
- 复杂度: 低

## 方案 B: 主从表
- 优势: 灵活，易扩展
- 劣势: 查询复杂
- 复杂度: 中

## 方案 C: NoSQL 文档存储
- 优势: 高度灵活
- 劣势: 学习成本高
- 复杂度: 高

推荐: 方案 B（平衡灵活性和复杂度）
```

### 步骤 4: 分段展示设计

**不要一次性展示全部设计**。分段获得反馈：

1. **先展示架构概览**
   - 系统分层
   - 核心模块
   - 数据流向

2. **等待用户确认**

3. **再展示详细设计**
   - 数据模型
   - API 接口
   - 前端页面

4. **获得最终批准**

### 步骤 5: 编写设计文档

**文档结构**:

```markdown
# {功能名称} 设计文档

## 1. 概述
- 业务目标
- 用户价值
- 范围边界

## 2. 架构设计
- 系统架构图
- 技术选型
- 模块划分

## 3. 数据模型
- 表结构设计
- 字段说明
- 索引设计

## 4. API 设计
- 接口列表
- 请求/响应格式
- 错误处理

## 5. 前端设计
- 页面结构
- 组件划分
- 交互流程

## 6. 非功能需求
- 性能要求
- 安全考虑
- 可用性要求

## 7. 风险与假设
- 技术风险
- 业务假设
- 依赖项

## 8. 验收标准
- 功能验收
- 性能验收
- 安全验收
```

### 步骤 6: 设计自我审查

在提交给用户前，自己检查：

**检查清单**:
- [ ] 设计完整，无遗漏关键部分
- [ ] 数据模型合理，符合规范
- [ ] API 设计清晰，遵循 REST
- [ ] 前端设计可行，符合 UI 规范
- [ ] 考虑了异常处理
- [ ] 明确了性能要求
- [ ] 识别了技术风险
- [ ] 验收标准可量化

**发现问题**:
- 立即修复
- 重新审查
- 确保质量

### 步骤 7: 用户审查设计文档

**提交审查**:
```markdown
# 设计文档已完成

请审查以下设计文档：
[设计文档内容]

## 关键决策
1. {决策 1}
2. {决策 2}
3. {决策 3}

## 需要确认的点
1. {确认点 1}
2. {确认点 2}

请批准设计或提出修改意见。
```

**等待用户响应**:
- 批准 → 步骤 8
- 修改 → 返回步骤 3 或 4

### 步骤 8: 保存设计文档

**保存到**:
```
docs/designs/{YYYY-MM-DD}-{feature-name}.md
```

**文档包含**:
- 完整设计内容
- 用户批准记录
- 设计决策理由

### 步骤 9: 过渡到实施计划

**终止状态**: 调用 `yuheng-spec-to-plan`

**禁止**:
- ❌ 调用任何其他实现 Skill
- ❌ 直接编写代码
- ❌ 跳过计划阶段

**唯一出口**:
```
yuheng-brainstorming → yuheng-spec-to-plan → yuheng-delivery-execution
```

## 硬门禁规则

### 禁止跳过设计

**无论任务看起来多么简单，都必须**:
1. 完成需求澄清
2. 提出多个方案
3. 展示设计
4. 获得用户批准
5. 编写设计文档

**违反后果**:
- 可能方向错误
- 浪费实现时间
- 需要返工

### 禁止直接实现

**在设计批准前，禁止**:
- 编写任何生产代码
- 创建任何文件
- 修改任何现有代码
- 运行任何脚手架
- 调用任何实现 Skill

## 关键原则

### 1. 一次一个问题

不要问：
```
1. 用户角色是什么？
2. 需要哪些功能？
3. 性能要求如何？
4. 安全级别是什么？
```

要问：
```
Q: 这个功能主要给哪类用户使用？
   A) 管理员
   B) 普通用户
   C) 两者都是
   
(等待回答后再问下一个)
```

### 2. 多选题优先

**优先级**:
1. 多选题（A/B/C）
2. 是/否问题
3. 开放性问题

**理由**: 降低用户负担，更容易回答

### 3. 必须有方案对比

**不要**:
```
我建议使用 Redis 做缓存。
```

**要**:
```
## 缓存方案对比

### 方案 A: Redis
- 优势: 性能高，功能丰富
- 劣势: 需要额外服务
- 推荐指数: ⭐⭐⭐⭐⭐

### 方案 B: 本地缓存
- 优势: 简单，无依赖
- 劣势: 集群不一致
- 推荐指数: ⭐⭐⭐

推荐: 方案 A（性能和功能更优）
```

### 4. 分段验证

**不要**: 一次性展示 20 页设计

**要**: 
1. 先展示架构（2 段）
2. 等待确认
3. 再展示细节（5 段）
4. 获得批准

## 使用示例

### 示例 1: 简单功能

**用户**: "添加一个用户导出功能"

**AI 执行**:
```
[步骤 1: 探索上下文]
检查现有用户管理模块...

[步骤 2: 澄清问题]
Q: 导出格式需要哪种？
   A) Excel
   B) CSV
   C) PDF
   D) 多种格式

用户: A) Excel

Q: 数据量大概多少？
   A) 小于 1000 条
   B) 1000-10000 条
   C) 10000 条以上

用户: B) 1000-10000 条

[步骤 3: 方案对比]
## 方案 A: 同步导出
- 优势: 实现简单
- 劣势: 大数据量会超时
- 推荐: ⭐⭐⭐

## 方案 B: 异步导出
- 优势: 不阻塞，支持大数据
- 劣势: 实现复杂
- 推荐: ⭐⭐⭐⭐⭐

推荐方案 B

[步骤 4: 展示设计]
...

[步骤 5-9: 完成剩余步骤]
```
