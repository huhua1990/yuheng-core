# 设计门禁规则

适用范围：所有创造性开发工作（新增功能、组件、修改行为）

---

## 强制规则

### 1. 任何创造性工作必须先完成设计

**创造性工作包括**:
- 新增功能
- 新增页面/组件
- 修改系统行为
- 架构调整
- 数据模型变更

**必须先**:
1. 完成需求澄清
2. 提出多个方案
3. 展示设计
4. 获得用户批准
5. 编写设计文档

### 2. 禁止"太简单不需要设计"

**反模式**:
```
"这只是个简单的 CRUD，不需要设计"
"就加个字段，直接改就行"
"配置修改而已，不用设计"
```

**正确做法**:
- 即使简单任务也要完成设计流程
- 设计可以简短，但必须存在
- 必须展示并获得批准

**原因**:
- 简单任务往往隐藏复杂性
- 未经审查的假设导致返工
- 确保与现有系统一致

### 3. 设计批准前禁止实现

**在用户批准设计之前，禁止**:
- 编写任何生产代码
- 创建任何文件
- 修改任何现有代码
- 运行任何脚手架
- 调用任何实现 Skill

**违反后果**:
- 方向错误需要返工
- 浪费实现时间
- 可能与系统冲突

## 设计最小要求

### 简单任务（< 1小时）

**最小设计包含**:
- 1-2 段功能描述
- 涉及的文件/模块
- 主要变更点
- 验收标准

**示例**:
```markdown
# 添加用户状态筛选

## 功能
在用户列表页添加状态筛选下拉框，可选：全部/正常/停用

## 变更
- 前端：views/system/user/index.vue 添加筛选组件
- 后端：UserPageReqDTO 添加 status 字段
- 查询：UserMapper.selectPage 添加状态条件

## 验收
- 筛选器显示正确
- 筛选结果准确
```

### 中等任务（1-4小时）

**设计包含**:
- 业务目标
- 数据模型变更
- API 接口设计
- 前端页面设计
- 验收标准

### 复杂任务（> 4小时）

**完整设计文档**:
- 概述
- 架构设计
- 数据模型
- API 设计
- 前端设计
- 非功能需求
- 风险识别
- 验收标准

## 工作流集成

### 标准流程

```
用户需求
    ↓
yuheng-brainstorming
    ├─ 澄清需求
    ├─ 方案对比
    ├─ 展示设计
    ├─ 获得批准 ← 【设计门禁】
    └─ 编写文档
    ↓
yuheng-spec-to-plan
    ↓
yuheng-delivery-execution
```

### 门禁检查点

**在进入 spec-to-plan 之前**:
- [ ] 设计已展示
- [ ] 用户已批准
- [ ] 设计文档已编写
- [ ] 设计文档已保存

**未通过门禁**:
- 返回 brainstorming
- 重新澄清或调整设计
- 再次获得批准

---

## AI 行为约束

### 必须做

1. **每个创造性任务**都调用 `yuheng-brainstorming`
2. **展示设计**并等待用户批准
3. **编写设计文档**并保存
4. 批准后才调用 `yuheng-spec-to-plan`

### 禁止做

1. ❌ 跳过设计直接编码
2. ❌ 认为任务"太简单"而省略设计
3. ❌ 在用户批准前开始实现
4. ❌ 展示设计后不等待批准就继续

---

## 豁免情况

### 以下情况可以豁免设计门禁

1. **纯 Bug 修复**
   - 不改变功能行为
   - 只修复现有功能的错误

2. **文档更新**
   - 只更新注释、README
   - 不涉及代码逻辑

3. **依赖升级**
   - 只升级依赖版本
   - 不改变功能

4. **代码格式化**
   - 只调整格式
   - 不改变逻辑

**注意**: 即使豁免，也要说明变更范围和影响

---

## 违反检测

### AI 自查清单

执行任何创造性工作前，检查：
- [ ] 是否调用了 brainstorming？
- [ ] 是否展示了设计？
- [ ] 用户是否批准了？
- [ ] 设计文档是否存在？

**如果任何一项为否** → 立即停止，返回 brainstorming
